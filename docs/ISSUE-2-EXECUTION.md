## Phase C — policy governance and internal authorization

Implemented Policy Management Center and server-side lifecycle controls: draft, evidence verification, conflict analysis, testing, independent supervisor approval, separate clinical-authority approval, publication/monitoring, rejection, evidence request, suspension and rollback. Existing Keycloak identities map reviewer to clerk, admin to supervisor/publisher, advisor to clinical authority. These are synthetic demonstration roles, not qualified clinical sign-off. Admin cannot substitute for the distinct clinical authority. Self-approval is rejected.

Policy originals, publication events, command receipts and internal authorization decisions are append-only. Drafts reference immutable source hashes. Optimistic version checks reject stale transitions, competing publications conflict, UUID command receipts reject altered replays, and identical retries return the committed result. Pending proposals do not change active evaluations. The original CQF clinical criteria are unchanged; the new published policy controls only a clearly labeled synthetic documentation review.

The encounter's separate Authorization Review panel shows active requirements, missing evidence, source citations and decision history. Authorized reviewers can request information, escalate to the advisor workflow, or approve an internal next step. An approval requires a current assessment, refreshed FHIR source hash, current policy revision and complete unsuspended requirements. Internal decisions never imply payer approval or change the source encounter status. Historical decisions are marked stale after source/policy changes. An information request works even before assessment, and reassessment of unchanged evidence preserves the pending request.

New API routes (authenticated): GET `/api/policy-center`; POST `/api/policy-changes`; POST `/api/policy-changes/:id/actions`; POST `/api/policy-suspension`; GET/POST `/api/cases/:id/authorization-review`. Existing routes remain compatible. All mutation schemas reject unknown fields and require event IDs; transitions additionally require the expected version/revision.

## Phase D — measured reliability, repair and optimization

The accepted thresholds are in RELIABILITY-ACCEPTANCE.md. Backup, load and reconciliation use a separate restored PostgreSQL database and loopback API instance. The working six-case database is not reset or used as the load generator's write target.

A real fault injected after FHIR success but before the PostgreSQL case update reproduced three Claim resources for one logical event (two failed attempts and successful retry). That run is a recorded failure. Reused Medplum's conditional-create API with a case/event identifier and payload fingerprint; the same fault sequence then produced one Claim and one committed event. Changed-payload receipts are rejected. The injected legacy receipts are retained as clearly identified synthetic fault evidence; they are not silently erased. Full distributed transaction orchestration/HA is not claimed.

First 25-session load run failed all gates except restart/restore: 600 failed/timed-out requests and p95 ~5.37s. The failure artifact is retained. SQL plan measurement showed repeated JSON-based sorting/projection; an expression index was added and the original thresholds rerun. Further outcomes are recorded only after completion.

Prometheus-compatible HTTP histograms and dependency-health alert evaluation extend the existing prom-client/Grafana stack. OpenTelemetry request/upstream spans use W3C context and a local source-free exporter. Installed SDK-trace-node 2.2 was deprecated; investigated the maintained SDK-trace 3.0/API 1.10 replacement, verified Node >=22.15 and peer compatibility, and used that combination. No external collector or patient payload export is configured. Temporal/Kubernetes/Chaos Mesh/Testcontainers are not added: existing PostgreSQL transactions, actual isolated restore databases and controlled Compose fault tests cover this narrow slice without redundant infrastructure.

The expression-index-only rerun also failed: 1,507 requests, throughput ~12.39/s, 6.90% timeouts, p95 ~5.00s. Failure evidence is retained separately. Deep offsets still incurred JSON projection/sort overhead. Replaced the repeated computed sort key with a PostgreSQL generated priority column plus a covering index, and materialized the bounded page before projecting FHIR summary fields. This preserves existing priority ordering and full-bundle API semantics while preventing discarded rows from paying projection cost. The original load thresholds remain unchanged for the next rerun.

The final bounded-API load rerun passed the original gates: 7,457 responses over 120.36s, 61.96/s, p95 743.23ms, p99 1,119.00ms, maximum 2,589.04ms, zero failed requests. Peak API RSS was 178,880,512 bytes; average API CPU ~19.07% of one core. API restart/readiness took 2.32s. A real restore into another isolated database took 2.66s and exactly matched six original cases and all 413 saved audit events/hashes. The six-case working database/audit remained unchanged throughout the load interval. These measurements cover one local paginated API and 25 distinct sessions of the same synthetic reviewer role; they do not certify 10,000 independent clinical/FHIR records or the legacy full-bundle UI.
